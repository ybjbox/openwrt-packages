# 自建测速端点：可行边界

> 记录时间 2026-11-20。所有数字都是在设备（10.0.0.1）上实测得到的，不是推测。

## 一句话结论

自建端点**只能**挂在 Cloudflare 免费子域（`*.workers.dev` / `*.pages.dev`）上。
挂**Worker 自定义域**在池外边缘 IP 上会被 CF 拒绝（403 + `error code: 1034`），
与插件 `--resolve` 钉候选 IP 的模型直接冲突。

> 2026-11-20 夜修正：1034 的适用范围比这里原先写的窄。别人 zone 上的**普通回源记录**
> 跨池是通的（`testfileorg.netwet.net` 500 MB 的 .zip 在 5 个池外 IP 上全 206）。
> 所以 1034 更像是「Worker / 隧道类自定义域只部署在 Worker 数据面那批 IP 上」，
> 而不是「用户 zone 一律不通」。自己 zone 上挂普通回源记录（nginx 直出）尚未实测。

## 三条路径的实测对照

| 端点 | 池内 IP | 池外 IP | 能否配 `--resolve` |
|---|---|---|---|
| `www.cloudflare.com`（CF 自有 zone，对照组） | 200 / 1334662 B | **200** / 1334662 B | ✅ |
| `st.xy-nas.eu.org`（用户 zone 自定义域） | 200 / 1048576 B | **403 / 17 B**（`error code: 1034`） | ❌ |
| `zzz-noexist.pages.dev`（CF 自有免费子域） | 530（项目不存在，但边缘已受理） | **530** | ✅ |

池外 IP 集合涵盖 5 个不同的 CF anycast 池：`172.64.52.143`、`104.16.132.229`、
`198.41.211.93`、`188.114.97.3`、`162.159.140.1`；池内为 `104.21.65.176`、
`172.67.147.224`（该 zone 的 A 记录）。

## 1034 是什么

CF 把用户 zone 部署到某一个 anycast 池（本例是 `104.21.0.0/16` + `172.67.0.0/16`）。
请求落到其它池的边缘时，边缘上根本没有这个 zone，于是回 `403` + 17 字节
（body 为 `error code: 1034`，即 Edge IP Restricted）。

这解释了 2026-10-17 那次「自建端点测速整列未测出」：不是 Worker 写错了，
也不是被 OpenClash 分流，而是**用了自定义域**。当时换回 `speed.cloudflare.com`
就恢复了，于是被误记成「Worker 方案不可行」。

## 为什么免费子域不受此限

`workers.dev`、`pages.dev` 是 Cloudflare 自有的 zone，和 `speed.cloudflare.com`
一样在所有 anycast IP 上服务，所以 `--resolve` 钉哪颗都成立。

顺带排除一个假象：`speedtest.cmliussss.workers.dev` 在本网络 TLS 握手直接失败
（`code=000`），但 `zzz-noexist.workers.dev` 正常回 530。说明失败是该 hostname
自身的问题（第三方 Worker 已失效/被收回），**不是 workers.dev 整域被阻断**。

## 与 speed.cloudflare.com 的取舍

| | `speed.cloudflare.com` | 自建 `*.workers.dev` |
|---|---|---|
| 跨池可用 | ✅ | ✅ |
| 限流 | 按**出口 IP** 计，约 270–330 MB / 滚动小时，429 | 无（自己控制） |
| 测的路径 | 边缘 → 客户端（含 CF 侧缓存/回源差异） | 边缘就地生成，纯下行 |
| 维护 | 无 | 需要一个 Worker |
| 历史数据可比性 | 基线 | **不可与前者直接比大小** |

## 落地要点

- Worker 代码与验收脚本见仓库根目录 `spdendpoint/`（不在本包内）。
- `speed_domain` / `speed_path` 是 uci 配置项，**切换端点不需要重装包**。
- 切换到自建端点后，`speed_bytes` 的实际值以 Worker 返回为准；
  `speed_valid` 要求响应 ≥1% 请求量，Worker 返回精确字节数自然满足。
- 必须带 `Cache-Control: no-transform`：否则全零响应会被 CF 压缩，
  吞吐虚高几十倍（`no-transform` 是 CF 关闭压缩的开关）。

## 2026-11-20 夜：改走 Pages（已落地）

`workers.dev` 在这台账号上彻底不可用：官方 Hello World 模板（ESM、819 B、无 flag、
`compat 2026-11-20`）原样部署仍是 `500 / error code: 1101`，而 Dashboard 预览能返回
`ok v2`。GraphQL 里 11-20 起全是 `scriptThrewException` 且 `scriptName: __unknown__`
——脚本名都没解析出来，死在加载阶段，属账号侧分发故障，与代码无关。

**Pages 走的是另一条分发面，同账号下正常。**

- 项目 `cfst` → **`cfst-4s1.pages.dev`**；部署方式为「高级模式」：根目录一个 `_worker.js`，
  内容就是 `spdendpoint/worker.js`（ESM，`export default { fetch }`），不需要构建。
- 部署脚本：`spdendpoint/pages-deploy.mjs`（纯内置 fetch/FormData，无 wrangler）。
  两个 API 细节：① `/deployments` 的 multipart 必须带 `manifest` 字段，空对象 `{}` 也行；
  ② `_worker.js` 走**具名部件**，不占 manifest 条目。

实测（2026-11-20 22:0x）：

| 请求 | 结果 |
|---|---|
| `/` | 200 `ok v2`（6 B） |
| `/1048576` | 200，恰好 1048576 B |
| `HEAD /104857600` | 200，`Content-Length: 104857600`，`Cache-Control: no-store, no-transform` |
| 6 个 IP 跨 5 个 anycast 池 `--resolve` `/65536` | 全 200 / 65536 B |

限制（免费版 Functions）：**10 万请求/日**、CPU 10 ms/请求、内存 128 MB。
一轮 16 次下载绰绰有余；但内存卡住了 `speed_bytes`——`worker.js` 里 `MAX` 写 100 MiB
只是形式上限，实际别超过 ~32 MiB（100 MiB 的 Uint8Array + Response 拷贝会撞 128 MB）。

切换只需改 uci，不用重装包：

```sh
uci set cf_ipcheck.global.speed_domain='cfst-4s1.pages.dev'
uci set cf_ipcheck.global.speed_path='/{bytes}'
uci commit cf_ipcheck
```

## 附：issue #168 的代码不能照抄

原文（2022）用的是经典 Service Worker 写法 `addEventListener("fetch", …)`。
现在的 Workers / Pages 都按 ES Module 加载，模块顶层没有 `addEventListener`，
**加载阶段**就抛 ReferenceError —— 表现为 `500 / error code: 1101`，与账号状态无关。
本次 `sweet-shape-b6ab` 就是这一例（拉 `content/v2` 可看到部署的正是原文那段）。
ESM 版见 `spdendpoint/proxy-esm.js`（含 `?bytes=N` → Range 限流，反代大文件时不会拉爆）。

## 分档实验：10 / 16 / 32 MiB（2026-11-20 夜）

方法：同 4 颗 NRT IP（172.64.229.12/.2/.16/.18），每挡 3 遍，按轮转排布、偶数号 IP 跑反序，
抵消已知的遍序惩罚。数据 `tier-data.tsv`、分析 `tier-analyze.py`。

**结论一：10 MiB 仍然严重低估。** 同 IP 逐挡中位（MB/s，十进制）：

| IP | 10 MiB | 16 MiB | 32 MiB | 32/10 |
|---|---|---|---|---|
| .12 | 8.84 | 11.37 | 15.81 | 1.79 |
| .2 | 10.22 | 12.70 | 18.47 | 1.81 |
| .16 | 8.76 | 11.83 | 20.71 | 2.37 |

− 16/10 中位 1.26，32/10 中位 2.09（历史对照：4→10 MiB 是 1.76）。
即 10 MiB 只测到真值的一半左右，比原先估计的 88% 差得多——18 MB/s、200 ms RTT 下，
慢启动要 ~9 个 RTT 才撑满 BDP，10 MiB 根本跑不完这段。

**结论二：32 MiB 会踩 16 MiB 的停滞点。** 多次大传输在 15.3~17.5 MB 处**停止推进**，
降到 0.3 MB/s，被 `--max-time` 截断后就是一条垃圾样本。16 MiB 请求（恰好到边界为止）
12 次全部正常完成；>16 MiB 的 8 次里 2 次卡死。所以**不要上 32 MiB**。

**结论三：现生成字节的端点跑不了大文件。** `cfst`（`new Response(slab(n))`）在 15~17 MB 处
同样塌陷（复现 2 次），判断是免费套餐 10 ms CPU 限制卡住 body 生成。`cfstp`（反代版，
流式透传）不受此限：37 次下载 0 次 429、0 次字节不符，32 MiB 稳定在 13~21 MB/s。

**取舍**：`speed_bytes` 10 MiB → **16 MiB**（+26% 时长，换回约 26% 的数值），
`speed_domain=cfstp-cm0.pages.dev`、`speed_path=/500MB-CZIPtestfile.org.zip?bytes={bytes}`。
一轮流量 ≈ 粗筛 80 + 精测 16×2×10 = 400 MiB；Pages 不计流量，
若仍挂在 `speed.cloudflare.com` 上则必 429（阈值 270~330 MB/滚动小时）。

遗留风险：反代源是别人的文件（testfileorg），长期应改成自托管 16 MiB 文件
（飞牛 + CF 橙云，方案 2）——前提是先验证自己 zone 的普通回源记录跨池可用。

## 2026-11-20 深夜：Pages 静态资源（终局方案，已上线）

`cfstp`（反代第三方大文件）报废：上游 `cf-cache-status: DYNAMIC`，没被边缘缓存，
每次回源到别人服务器，实测 0.24 MB/s。改为**自己上传静态文件**即可，不需要任何源站。

**项目 `cfst` 系列最终形态**：`cfst16` → `cfst16.pages.dev`，纯静态资产（无 Function，
因此没有 10 ms CPU 限制）：

| 路径 | 字节数 | 用途 |
|---|---|---|
| `/4194304.zip` | 4 MiB | 粗筛（`speed_screen_bytes`） |
| `/10485760.zip` | 10 MiB | 兼容旧配置 |
| `/16777216.zip` | 16 MiB | 精测（`speed_confirm_bytes`） |

内容是不可压缩随机数据（全零可能被中间设备压缩，导致字节数与请求量对不上）。
路径模板 `/{bytes}.zip` 让三个档位各自命中对应文件。

### 部署的两个硬坑（都踩过）

1. **`POST /deployments` 的 multipart 只是索引，不含内容。** 资产要先走
   `GET /projects/{name}/upload-token` 拿 JWT，再 `POST /pages/assets/upload`
   （JSON，`{key, value:base64, metadata:{contentType}, base64:true}`），
   最后 `POST /pages/assets/upsert-hashes`。只发 manifest 的结果是**部署成功、访问 500**
   （不是 404 —— 清单里有这个路径，内容库里没有）。
2. **资产键是 BLAKE3，不是 SHA-256**：`blake3(base64(内容) + 扩展名)` 的 hex 前 **32** 位
   （`workers-utils/asset-hash`）。用 sha256 同样"上传成功"，同样是 500。Node 无内置
   BLAKE3，用 `hash-wasm`（`npm i hash-wasm`，装在 `E:/cf_ipcheck/node_modules`）。

脚本：`spdendpoint/deploy-assets.mjs`（`CF_TOKEN=xxx node deploy-assets.mjs cfst16`），
`spdendpoint/gen-static.mjs` 生成三个文件。旧的 `deploy-static.mjs`（只发 multipart）已删。

### 实测（2026-11-20 23:1x ~ 23:5x）

- 部署后首次请求 4 MiB 曾 500 约 30 秒（资产传播），此后稳定 200。
- 跨 5 个 anycast 池 `--resolve`（172.64.52.143 / 104.16.132.229 / 188.114.97.3 /
  162.159.140.1 / 104.21.65.176）全部 200，字节精确。
- 设备上 16 MiB 命中好的边缘时 4.0~4.1 MB/s（≈33 Mbps），差的边缘 0.6 MB/s ——
  差异来自线路双峰，与端点无关。
