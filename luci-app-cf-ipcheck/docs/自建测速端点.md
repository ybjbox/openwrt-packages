# 自建测速端点：可行边界

> 记录时间 2026-11-20。所有数字都是在设备（10.0.0.1）上实测得到的，不是推测。

## 一句话结论

自建端点**只能**挂在 Cloudflare 免费子域（`*.workers.dev` / `*.pages.dev`）上。
挂自己的域名（含 Worker 自定义域、橙云 A/CNAME）在池外边缘 IP 上会被 CF 拒绝，
与插件 `--resolve` 钉候选 IP 的模型直接冲突。

## 三条路径的实测对照

| 端点 | 池内 IP | 池外 IP | 能否配 `--resolve` |
|---|---|---|---|
| `www.cloudflare.com`（CF 自有 zone，对照组） | 200 / 1334662 B | **200** / 1334662 B | ✅ |
| `st.xy-nas.eu.org`（用户 zone 自定义域） | 200 / 1048576 B | **403 / 17 B**（`error code: 1034`） | ❌ |
| `zzz-noexist.pages.dev`（CF 自有免费子域） | 530（项目不存在，但边缘已受理） | **530** | ✅ |

池外 IP 集合涵盖 5 个不同的 CF anycast 池：`172.64.52.143`、`104.16.132.229`、
`198.41.211.93`、`188.114.97.3`、`162.159.140.1`；池内为 `104.21.65.176`、
`172.67.147.224`（该 zone 的 A 记录）。

## 1034 是什么

CF 把用户 zone 部署到某一个 anycast 池（本例是 `104.21.0.0/16` + `172.67.0.0/16`）。
请求落到其它池的边缘时，边缘上根本没有这个 zone，于是回 `403` + 17 字节
（body 为 `error code: 1034`，即 Edge IP Restricted）。

这解释了 2026-10-17 那次「自建端点测速整列未测出」：不是 Worker 写错了，
也不是被 OpenClash 分流，而是**用了自定义域**。当时换回 `speed.cloudflare.com`
就恢复了，于是被误记成「Worker 方案不可行」。

## 为什么免费子域不受此限

`workers.dev`、`pages.dev` 是 Cloudflare 自有的 zone，和 `speed.cloudflare.com`
一样在所有 anycast IP 上服务，所以 `--resolve` 钉哪颗都成立。

顺带排除一个假象：`speedtest.cmliussss.workers.dev` 在本网络 TLS 握手直接失败
（`code=000`），但 `zzz-noexist.workers.dev` 正常回 530。说明失败是该 hostname
自身的问题（第三方 Worker 已失效/被收回），**不是 workers.dev 整域被阻断**。

## 与 speed.cloudflare.com 的取舍

| | `speed.cloudflare.com` | 自建 `*.workers.dev` |
|---|---|---|
| 跨池可用 | ✅ | ✅ |
| 限流 | 按**出口 IP** 计，约 270–330 MB / 滚动小时，429 | 无（自己控制） |
| 测的路径 | 边缘 → 客户端（含 CF 侧缓存/回源差异） | 边缘就地生成，纯下行 |
| 维护 | 无 | 需要一个 Worker |
| 历史数据可比性 | 基线 | **不可与前者直接比大小** |

## 落地要点

- Worker 代码与验收脚本见仓库根目录 `spdendpoint/`（不在本包内）。
- `speed_domain` / `speed_path` 是 uci 配置项，**切换端点不需要重装包**。
- 切换到自建端点后，`speed_bytes` 的实际值以 Worker 返回为准；
  `speed_valid` 要求响应 ≥1% 请求量，Worker 返回精确字节数自然满足。
- 必须带 `Cache-Control: no-transform`：否则全零响应会被 CF 压缩，
  吞吐虚高几十倍（`no-transform` 是 CF 关闭压缩的开关）。
