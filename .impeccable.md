# Design Context — luci-app-cf-ipcheck

## Design Context

### Users

Self-hosting power users who run OpenWrt on their own router (primary user: one person,
Ryan — a home-lab operator with an Athena / IPQ6010 device). They open this page for one
of exactly three reasons:

1. **"Which IP should I use right now?"** — they came to read the leaderboard and copy IPs.
2. **"Why is the leaderboard empty / stale?"** — they suspect the candidate sources broke.
3. **"I want to change a threshold."** — they tune TTFB / total limits, then want proof.

Context of use: **a browser on a phone or laptop — on the LAN at home, or remotely
through the public LuCI at `https://op.403333.xyz:8888` when away**. Sessions are short
and goal-driven. The page is opened many times over months but each visit lasts under a
minute. The user is technical — they know what TTFB and colo codes mean — but they are
not reading the page; they are *scanning a readout*. Errors here mean a broken proxy, so
trust and legibility matter more than delight. Remote access makes the page latency-prone:
it must remain readable before it becomes decorative.

### Brand Personality

**Precise. Instrumental. Unembellished.**

The voice is that of good instrumentation: it states readings, not opinions. It never
sells, never apologises, never uses exclamation marks. Copy is declarative and specific
("候选池 122 个", not "正在获取候选池…"). If the engine cannot produce a number, the page
says why in engineering terms and offers the one action that would fix it.

The emotional goal is **confidence through legibility** — the feeling of reading a piece
of equipment that is clearly telling the truth.

### Aesthetic Direction

**Industrial control panel / instrumentation.**

Reference feel: the readout face of a network appliance, a bench oscilloscope, a rack
unit's status LEDs, `htop` and `btop` as executed by a designer. Not skeuomorphic — no
fake bevels or faux brushed metal — but *derived from* the discipline of instrument
design: strict alignment, monospaced figures, hairline rules instead of boxes, a
restrained signal palette where colour carries state and nothing else.

**Anti-references** (what this must NOT become):
- Neon-on-black "hacker terminal" cosplay; glowing cyan on pure black.
- Generic AI dashboard: purple→blue gradient, glassmorphism cards, rounded-everything.
- Marketing hero-metric template: one giant number floating in white space.
- Bootstrap-admin look: every section in a card, every card with a shadow.
- Anything that prioritises a decorative effect over reading a number correctly.
- **A full visual-direction rewrite.** The “night-shift instrument console” candidate
  (graphite canvas, ink primary, outline badges) was rejected by the user. Do not
  reintroduce it as a “new direction”; improve the existing Argon/card surface only.

### Design Principles

1. **The reading is the interface.** Numbers are the primary content, so they get the
   strongest treatment: monospaced/tabular figures, right-aligned so digits line up
   column-wise, and enough size contrast that the leaderboard is legible at a glance.
2. **Colour is a signal, never a decoration.** One hue family carries state
   (running / ok / warn / bad) and one carries the single primary action. Everything
   else is a neutral. If a colour is not reporting a condition, it must not be there.
3. **Hairlines, not boxes.** Structure comes from alignment, spacing and 1px rules.
   Cards are used only where content is genuinely a separate object; never nest them.
4. **Say the true thing.** A failed readout must never be dressed as an empty result.
   Distinguish "never ran", "ran and found nothing", and "could not run" explicitly,
   and pair every empty state with the action that resolves it.
5. **Density with air.** This is a data tool, so information density is a feature — but
   rhythm comes from consistent 4pt-scale spacing and a 5-step type scale, not from
   cramming. Run, diagnostics and logs fit one screen at desktop width; settings is
   allowed to scroll because it is a form, not a readout (32 fields across 5 visible
   groups at r177, 12 of them behind the single "advanced" group; the 33rd field,
   sources, lives on Diagnostics).

### Current implementation (r177)

The shipped UI is the **existing Argon shell + r140 card surface**, not a new visual
direction. The latest pass is incremental:

- Settings: 33 fields; 21 fields removed from the page (uci/engine kept), 12 in
  “高级设置”, 20 always visible; source list stays on Diagnostics; DNS stays single
  column while other simple groups use two columns at ≥1200px. Dependencies hide
  DNS/Gist/speed/token-file rows with `speed_gate`/`speed_probe`/`dns_sync`/`upload_gist`.
- Run: 1024 table header restored, 420 throughput label/bar/value on one line, 10px
  labels raised to 11px, quality column shows `ms`, first-place marker is an outline
  badge (no duplicate first-row bar).
- Logs: desktop toolbar is two groups (“modes” and “actions”); mobile returns to the
  original compact wrapping via `display: contents`.
- CSS: no `:is()` selectors; explicit `[data-group]` lists; CssTidy-safe.
- Browser: the view asset `?v=` tracks luci-base, not this package — hard refresh after
  install; verify with a fresh/cache-disabled context.
- Constraints: no new dependencies, no new settings UI beyond the 33, no full redesign,
  no hidden uci knobs re-exposed. The user wants low-chrome, visible button boundaries,
  concise logs, and settings that are pickable rather than free text where possible.
